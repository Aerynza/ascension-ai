# Native AI production replacement attestation

The native runtime can load a real GGUF checkpoint independently of third-party inference. **Being loaded is not proof of replacement quality, complete tooling, or execution of the 640 catalog capabilities.**

## Release gate

`src/core/release_gate.py` keeps `replacement_ready=false` until all of the following are true:

1. The exact release profile `pro_v231` is loaded and the pinned `sha256` is known. New merged checkpoints require a separately reviewed profile and attestation gate update.
2. An evaluation attestation exists at `evals/results/production_replacement_attestation.json`.
3. The attestation covers the exact `profile` and `model_sha256`, carries a trusted CI run URL, and was issued within the past seven days.
4. Every defined gate has an actual Boolean passing result: conversation quality, shell isolation, action integrity, domain reasoning, safety/privacy, interactive latency, concurrency recovery, and native-primary canary.
5. The complete payload has a valid HMAC-SHA256 signature generated by the evaluation/release authority using `ASCENSION_AI_READINESS_ATTESTATION_KEY_BASE64`, a deployment secret of at least 32 bytes.
6. The operator explicitly sets `ASCENSION_NATIVE_REPLACEMENT_APPROVED=true` **after reviewing the receipts**.

An uploaded JSON file, static capability count or environment switch alone is insufficient. No test secrets, model weights or real user data belong in Git. Keep attestation signing material outside training containers and never commit it.

## Evidence structure

```json
{
  "payload": {
    "suite": "aerynza_native_replacement_v1",
    "profile": "pro_v231",
    "model_sha256": "<the exact pinned 64-hex digest>",
    "issued_at": 0,
    "expires_at": 0,
    "evaluation_cases": 20,
    "ci_run_url": "https://github.com/acensionlifeos-dev/ascension-ai/actions/runs/12345",
    "gates": {
      "conversation_quality": true,
      "shell_isolation": true,
      "action_integrity": true,
      "domain_reasoning": true,
      "safety_privacy": true,
      "interactive_latency": true,
      "concurrency_recovery": true,
      "native_primary_canary": true
    }
  },
  "signature": "<64-character HMAC-SHA256 hex digest>"
}
```

This is a **schema example, not a passing evaluation**. Its timestamps, digest and signature are deliberately invalid. Gate outcomes must come from executed model and integration tests, not handwritten values.

The HMAC message is UTF-8 JSON of `payload` with sorted keys, no extra spaces and preserved Unicode. Its key is the Base64-decoded secret. The API rejects invalid, stale, mismatched, unsigned and incompletely evaluated records. `candidate_ready` reflects only whether the model is loaded; `replacement_ready` reflects the attested operator release gate.

The 640-capability report is a catalog. Real user permission, connected provider, approved action, independently verified receipt, persistence, and recovery are still required for each externally consequential action. Keep outside-provider fallback available until the attested native gate passes all tests on the actual deployment.
